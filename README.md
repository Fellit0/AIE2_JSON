# Парсер и анализатор JSON-логов LLM

В этом проекте ты продолжишь работать с одним из основных форматов файлов — JSON. На этот раз ты научишься работать с JSON-логами вызовов LLM — извлекать, фильтровать и агрегировать данные о производительности. Ты освоишь парсинг структур с вложенными полями, обработку пропусков и ошибок, а также расчёт ключевых метрик (токены, задержки).

Полученные навыки помогут тебе в дальнейшем при мониторинге AI-сервисов, анализе cost efficiency и отладке RAG-систем — востребованных задачах в LLMOps и production-инженерии.

## Chapter I

11:00. Неожиданная задача.

Ты — AI-инженер в команде, которая разрабатывает внутренний RAG-сервис для поддержки клиентов. Вчера твой коллега запустил нагрузочное тестирование новой версии промптов и сохранил логи вызовов LLM в JSON-файл. Сегодня утром приходит сообщение от тимлида:

_«Сервис работал сутки, но у нас нет метрик — только сырые логи. Нужно понять, не упала ли производительность, сколько токенов мы сожгли и были ли аномальные задержки. Напиши утилиту, которая проанализирует логи и выдаст понятный отчёт»._

Ты открываешь файл и видишь записи вроде:

```json
{"timestamp": "2025-02-18T10:23:01", "prompt": "...", "response": "...", "tokens_used": 1450, "latency_ms": 320}
{"timestamp": "2025-02-18T10:25:10", "prompt": "...", "tokens_used": 890, "latency_ms": 205, "error": "timeout"}
```

Проблема: логи содержат не только успешные вызовы, но и ошибки, иногда отсутствуют некоторые поля (например, `response` при ошибке). Плюс нет чёткого понимания, что считать «аномалией» и какой порог токенов считать «тяжёлым» запросом.

Твоя задача — написать Python-скрипт, который превратит этот хаос в структурированный анализ. Ты будешь двигаться итеративно, выполняя три последовательных задания.

## Chapter II

В этом проекте ты потренируешься:

- Читать и парсить JSON-файлы с неоднородной структурой.
- Фильтровать записи по пользовательским критериям.
- Рассчитывать агрегированные метрики (суммы, средние, процентили) и выявлять выбросы.
- Обрабатывать ошибки и пропущенные поля, не допуская падения скрипта.
- Оформлять вывод в виде JSON-отчёта и текстового `README` с рефлексией.

Важно: нет единственного «правильного» набора метрик или порогов. Ты самостоятельно выбираешь, на что обратить внимание, и обосновываешь свой выбор в отчёте. Такой подход приближен к реальной работе, где требования часто размыты, а инженерное решение требует аргументации.

## Задание 1. Парсинг и базовая фильтрация логов

Цель: научиться загружать JSON-логи, отбирать только те записи, которые удовлетворяют критерию по токенам, и сохранять промежуточный результат.

Что нужно сделать:

1.  Создай в папке `data/` файл `logs.json` с 20–30 записями (формат JSON lines), имитирующими вызовы LLM. Каждая запись должна содержать как минимум:
    - `timestamp` (строка в ISO-формате)
    - `tokens_used` (целое число, может отсутствовать)
    - `latency_ms` (целое число, может отсутствовать)
    - опционально: `error`, `prompt`, `response`, `model`.
2.  Добавь несколько записей с ошибками и несколько — без поля `tokens_used` или `latency_ms`.
3.  Напиши Python-скрипт `parse_llm_logs.py`, который:
    - Загружает `data/logs.json`.
    - Если файл пуст, повреждён или содержит невалидный JSON — выводит сообщение в `stderr` и завершается с кодом ошибки.
    - Отбирает (фильтрует) записи, у которых `tokens_used` превышает заданный порог.
    - Рекомендуемый порог — 1000. Если ты выбираешь другой — зафиксируй его как константу и подготовься обосновать в `README`.
    - Сохраняет отфильтрованные записи в файл `results/filtered_logs.json` (полностью, с сохранением исходной структуры каждой записи).
4.  В консоль (`stdout`) скрипт должен выводить:
    - Общее количество обработанных записей.
    - Количество записей, прошедших фильтр.
    - Выбранный порог.

Результат сдачи задания 1:

- Код скрипта (пока может быть без полного набора метрик, только фильтрация).
- Файл `data/logs.json` и `results/filtered_logs.json`.
- Краткое описание в `README` (можно дополнить позже).

## Задание 2. Расчёт метрик и генерация JSON-отчёта

Цель: дополнить скрипт вычислением агрегатных метрик по отфильтрованным записям и выводом их в формате JSON.

Что нужно сделать (дополнить скрипт из задания 1):

1.  Из отфильтрованных записей (тех, что прошли порог по токенам) рассчитай:
    - Сумму токенов (`total_tokens`) — сумма всех `tokens_used`.
    - Среднюю задержку (`avg_latency_ms`) — среднее арифметическое `latency_ms`. Если у записи нет поля `latency_ms`, она игнорируется для этой метрики (но не отбрасывается полностью).
    - Одну дополнительную метрику задержки на выбор (медиану, 90-й перцентиль, 95-й перцентиль, минимум или максимум).
2.  Сформируй JSON-отчёт и сохрани его в `results/report.json`. Минимальная структура:

```json

{
    "total_entries": 30,
    "filtered_entries": 12,
    "token_threshold": 1000,
    "total_tokens": 15600,
    "avg_latency_ms": 345.6,
    "extra_latency_metric": {"name": "p95_latency_ms", "value": 512}

}
```

При необходимости добавь другие поля (количество ошибок, средний токен на успешный запрос и т.п.).

1.  Скрипт должен обрабатывать случаи, когда после фильтрации не осталось записей — тогда метрики задержки и сумма токенов могут быть `null` или `0`, но отчёт должен быть валидным JSON.

Результат сдачи задания 2:

- Дополненный скрипт (теперь содержит всю логику).
- Файл `results/report.json` (сгенерированный).
- В `README` — обоснование выбора дополнительной метрики и порога фильтрации.

## Задание 3. Обработка ошибок и документация

Цель: сделать скрипт устойчивым к реальным «грязным» данным, добавить обработку исключительных ситуаций и оформить полноценную документацию.

Что нужно сделать (доработать скрипт из задания 2):

1.  Устойчивость к некорректным данным:
    - Если значение `tokens_used` не является числом (например, строка) — пропустить эту запись при расчёте суммы токенов и фильтрации, но не прерывать выполнение скрипта. Записать предупреждение в `stderr` (или в отдельное поле отчёта, например, `warnings`).
    - Аналогично для `latency_ms`.
    - Если в JSON-файле встретилась строка, не являющаяся словарём — пропустить её с предупреждением.
    - При полностью пустом файле или отсутствии полей `tokens_used` у всех записей — выдать осмысленное сообщение и корректный (возможно, нулевой) отчёт.
2.  Документация (`README.md`) должна содержать:
    1.  Описание структуры входного JSON (какие поля ожидаются).
    2.  Команду запуска (например, `python parse_llm_logs.py`).
    3.  Обоснование выбора порога фильтрации и дополнительной метрики.
    4.  Описание того, как скрипт обрабатывает пропуски и ошибки (с примерами).

Результат сдачи задания 3 (итоговый):

- Финальная версия скрипта `parse_llm_logs.py`.
- `data/logs.json` (пример входных данных).
- `results/filtered_logs.json` и `results/report.json`.
- `README.md` с документацией

- Убедится, что скрипт не падает при отсутствии полей и выводит понятный отчёт.
- Оценит обоснованность инженерных выборов (порог, метрики, обработка ошибок) по `README`.
